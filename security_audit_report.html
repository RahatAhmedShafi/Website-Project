This report outlines the security architecture implemented on the Vibora Social Platform, mapping our design decisions directly to the security tools, frameworks, and case studies covered in the computer security syllabus.

Implemented Security Protections in Code

1. HTTP Security Headers Middleware (CSP, Clickjacking, HSTS)

File Location: backend/src/server.js (Lines 27–46)

This custom middleware intercepts all requests and sets security-hardening response headers:

  • Content-Security-Policy (CSP): Restricts script execution to 'self', blocking browser exploitation frameworks (such as BeEF) from executing remote hook injections.
  • X-Frame-Options: DENY: Stops framing/iframe-embedding to completely mitigate phishing and clickjacking overlays.
  • Strict-Transport-Security (HSTS): Forces the browser to connect exclusively over secure HTTPS channels, stopping man-in-the-middle credential hijacking.
  • X-Content-Type-Options: nosniff: Disables browser MIME-type sniffing to prevent text files from being parsed as executable scripts.

2. NoSQL Database Injection Sanitizer

File Location: backend/src/server.js (Lines 47–59)

To prevent authentication bypass queries (where adversaries inject operators like {"$ne": ""} into login parameters), we parse incoming body parameters recursively:

  • Recursively scans body payload objects.
  • Strips any key starting with a dollar sign ($) to neutralize NoSQL query injection payloads before they are passed to MongoDB.

3. Password Hashing Cryptography (BCrypt)

File Location: backend/src/routes/auth.js (Lines 28–29, 73)

Secures user password data stored in the database:

  • On Registration (Line 28–29): Uses bcrypt.genSalt(10) to generate a cryptographically strong salt, and hashes the password with bcrypt.hash().
  • On Login (Line 73): Compares the incoming plaintext password against the hashed string using bcrypt.compare(), ensuring plaintext credentials are never stored.

4. JWT Authentication Middleware (Route-Level Access Controls)

File Location: backend/src/middleware/auth.js (Lines 5–27)

Secures REST endpoints by requiring valid session signatures:

  • Checks incoming request headers for a valid Bearer <token> string.
  • Validates the signature using JSON Web Tokens (jwt.verify) and mounts the decoded user session to the request scope. Unauthenticated requests are rejected immediately with a 401 Unauthorized response.

5. Secure WebSockets Upgrade Handshake

File Location: backend/src/server.js (Lines 135–153)

Secures WebSocket message streams against hijacking:

  • Intercepts the HTTP upgrade handshake request and reads the authentication token from request query parameters.
  • Verifies token signatures using jwt.verify(). If verification fails or no token is provided, the TCP socket is immediately destroyed using socket.destroy().

Literature Review & Project Benchmark Analysis

To contextualize Vibora's academic contribution, we benchmark our localized architecture against traditional centralized and federated social media models.

1. Social Media Architecture Classifications (Literature Reference)

  • Traditional Centralized Social Networks (Facebook/Twitter Model):
    Reference Paper C: “Towards Privacy-Preserving Social-Media SDKs” (USENIX Security 2024).
    USENIX Security 2024 Publication Link
    Shortcomings: Large centralized networks inject third-party trackers and telemetry SDKs that harvest user device metadata and profile student location networks. This highlights why Vibora runs in a strictly sandboxed client web environment with zero external tracker dependencies.
  • Federated & Decentralized Networks (Mastodon/Diaspora Model):
    Reference Paper D: “Trouble in Paradise? Understanding Mastodon Admin’s Challenges” (ACM Human-Computer Interaction 2024).
    ACM CSCW 2024 Publication Link
    Shortcomings: Host administrators of decentralized nodes face security and moderation hurdles. Node servers are primary targets for database compromises, where attackers exploit host permissions to leak local user communications.

3. Core Shortcomings of Vibora (Project Limitations)

While Vibora is highly performant and secure against client-side exploitation, it has these limits:

  1. Plaintext Messages: Direct messaging logs are stored in plaintext in the JSON database, making them vulnerable if the host environment gets compromised (similar to federated networks).
  2. Brute Force Susceptibility: The backend currently lacks rate-limiting middleware, leaving login endpoints vulnerable to automated dictionary attacks.

4. Vibora's Novelty & Future Security Roadmap

Vibora's novelty lies in coupling coarse localized context (districts & universities) with zero-latency in-memory data retrieval to create a highly responsive social discovery space without compromising user privacy.

To resolve current limitations, our future development plan includes:

  1. End-to-End Encryption (E2EE): Implementing Diffie-Hellman key exchanges to encrypt direct messages client-side, ensuring chat logs cannot be read in plaintext by the database host.
  2. Zero-Knowledge District Verification: Utilizing zk-SNARKs to prove a user belongs to a specific district or university without sharing their raw geolocation data or institutional ID numbers.
  3. Token Bucket Rate-Limiting: Adding Express middleware rate-limiters to key auth paths to neutralize dictionary attacks.

Security Attribute Implementation Checklist

This checklist summarizes the current security attributes already implemented in Vibora's core features, alongside our post-demonstration roadmap (future security features to work on later).

1. Currently Implemented Security Attributes

  • User Authentication & Authorization: Secure credential hashing using BCrypt with unique salt rounds. State validation via JSON Web Tokens (JWT) on all protected API routes. Socket handshakes are validated via JWT query signatures before establishing real-time connections.
  • Input Sanitization (NoSQL Injection Defense): Recursive request body sanitizer in server.js that strips keys starting with $ to block MongoDB query injection attacks.
  • Client Exploitation Defenses: Content Security Policy (CSP) to block remote script executions (e.g. BeEF hook frameworks). X-Frame-Options: DENY to completely block clickjacking frame overlays. X-Content-Type-Options: nosniff to block MIME-type sniffing vulnerabilities.
  • Location Data Minimization: Matches users using coarse proximity groupings (Universities/Districts) rather than leaking raw GPS coordinate tracks.
  • In-Memory Database Shielding: Uses memory caches to isolate the primary database file from rapid, repeated API requests, mitigating database depletion DOS attacks.

2. Planned Security Attributes (To Work on Later)

  • Chat Cryptography (E2EE): Implement client-side encrypt/decrypt functions using Web Crypto APIs (AES-GCM/ECDH) to protect private chat messages from database eavesdropping.
  • Rate-Limiting Controls: Integrate express-rate-limit middleware on /api/auth login and registration paths to block brute force dictionary attacks.
  • Vetted File-Upload Vetting (MIME Sanitizer): Vetting file uploads (Photos/Avatar) to restrict formats strictly to JPEG, PNG, and WebP, checking file signature magic bytes to block remote command execution (RCE).
  • Role & Asset Ownership Validation: Refine asset validation middleware to ensure users cannot edit or delete posts belonging to other citizens by intercepting client payloads.
  • Two-Factor Authentication (2FA): Add optional Time-based One-Time Password (TOTP) codes via Google Authenticator during the sign-in flow.
